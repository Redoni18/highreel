# Highreel

Self-serve "Wrapped"-style recaps: a small business uploads a spreadsheet of customer stats and every customer gets a personal recap page to share. Named Highreel (highreel.app) on 2026-10-12; "Recap" was the working name.

**Read `SPEC.md` first.** It holds the product, the spreadsheet contract, the UI decisions, the data model and the milestones. Before ending a session, add a row to its §12 Status table.

**Moving off Supabase (SPEC M2.14, planned 2026-10-12):** the database, files and sign-in move to Cloudflare (D1, R2, Better Auth, one Worker). Landed 2026-10-12: P0 (the build is a Cloudflare Worker, `wrangler.jsonc`; dev emulates its bindings), P2 (files in R2) and P1 (data in D1), P2 first because Supabase Storage's rules read the businesses table. Landed 2026-10-13: P3 (sign-in on Better Auth, `server/utils/auth.ts`; nothing talks to Supabase any more) and P4 (scheduled jobs: old demos, requested account deletions, expired sign-in records; `server/tasks`, Cron Triggers). `supabase start` is still how Mailpit runs locally (sign-in links, recap emails) until P5 gives it its own command; P6 deletes `supabase/` and rewrites SPEC §7.

## Commands

```bash
corepack pnpm install
supabase start           # only for Mailpit (inbox http://127.0.0.1:54424, SMTP 54425) until M2.14 P5
corepack pnpm db:migrate # apply migrations/ to the local D1 database (.wrangler/state/v3); `db:reset` wipes it first (stop the dev server)
corepack pnpm dev        # http://localhost:3040 → "Try the demo" (anonymous session); /app home, /app/brand Your brand, /app/c/:id a recap (Sheet · /design · /share); recap emails (via "Local test inbox" on Your brand) land in Mailpit, http://127.0.0.1:54424
corepack pnpm sample     # regenerate public/templates/*.csv
corepack pnpm test       # vitest: validators, templates, mapping
corepack pnpm check:isolation  # two businesses through the API: B tries every workspace route with A's ids (needs the dev server)
corepack pnpm e2e        # browser checks in headless Chrome (needs the dev server and Mailpit)
corepack pnpm typecheck
corepack pnpm build      # the Worker (.output); `corepack pnpm exec wrangler dev --port 3047 --inspector-port 9339 --test-scheduled` runs it on workerd against the local D1/R2 (SPEC M2.14); `--test-scheduled` adds /__scheduled?cron=… to fire a Cron Trigger
curl -X POST http://localhost:3040/_nitro/tasks/cleanup:demo   # run a scheduled job now on the dev server (also cleanup:auth, accounts:delete; SPEC M2.14 P4)
node scripts/worker-sheets.mjs  # 10k/50k-row sheets on that Worker: time, CPU, heap (no request may grow it by 40 MB)
E2E_BASE=http://localhost:3047 node tests/e2e/budgets.mjs   # recap budgets, against that Worker (SPEC §7.6)
E2E_BASE=http://localhost:3047 node tests/e2e/record.mjs  # phone-size MP4s of an app and a visit recap → tests/e2e/.out
node scripts/perf-home.mjs  # GET /api/home at 10 campaigns × 10k rows on local D1 (budget 300 ms; needs the dev server)
node scripts/og-landing.mjs # redraw public/og.png (the landing's link preview)
node scripts/icons.mjs      # redraw favicon.ico, icon.svg, the touch/manifest icons, site.webmanifest and the logo files in brand/ (logo outlines: scripts/brand.mjs)
npx lighthouse@12.8.2 http://localhost:3047/ --form-factor=mobile --throttling-method=simulate --chrome-flags="--headless=new"   # and --preset=desktop; on the built Worker (SPEC §7.6)
python3 scripts/subset-caveat.py  # rebuild the landing's handwriting font subset (fonttools + brotli)
```

`pnpm` is not on PATH on this Mac; always go through `corepack pnpm`.

## Rules

- The product is **Highreel**: the lowercase wordmark, page titles ("Sign in · Highreel"), "Made with Highreel" on the share slide, share image and link preview, and anywhere copy names us. What each customer gets is **a Highreel** (plural Highreels; owner, 2026-10-12: the name should become the word for them, like Spotify's "Wrapped"). "highlight reel" only where a first-time reader needs it explained: the landing's headline, title, description and link preview, the lede that defines it ("their own Highreel: an animated highlight reel of their year"), the example pages' descriptions, and the first mention on terms and privacy (`landing.mjs` and `legal.mjs` check this). Everything else says Highreel: the whole app ("New Highreel", "195 Highreels published", toasts, errors, the sheet contract) and, since the owner's follow-up the same day, what the business's own customers receive too (the email button "Open your Highreel", the default WhatsApp text, the landing's inbox mock-ups, `/r`'s errors, the unsubscribe page, saved image names, the "customers got a Highreel" suggestion), so the word spreads like "my Wrapped". Those messages still come from the business: no Highreel sender, logo or footer in an email (`send.mjs` checks the button is its only mention). "recap" only as an ordinary word in a sentence, never as the noun. File names: `highreel-template-*.csv`, the links file's `link` column and the `{link}` placeholder (`{recap_url}` still works in saved messages). The repo folder and package are `highreel` (2026-10-12); the Supabase `project_id` (renaming it drops the local database), code names (`RecapPlayer`, `/r`, `recap.css`) and localStorage keys keep "recap".
- Verify UI changes in a real browser, not just by typecheck: `corepack pnpm e2e` (headless installed Chrome), and add a check to `tests/e2e/` for new behaviour. Claude in Chrome's window is often hidden on this Mac, which freezes animations.
- The workspace UI is a dense Airtable-style grid with a live recap preview. No dashboard cards, charts or stat tiles (SPEC §6).
- A recap's setup lives in its tabs (SPEC M2.6): Sheet is data and a preview only; wording, theme, photos and the button go in Design; publishing and sending in Share; name, logo and colour on Your brand. Don't add design controls back to the Sheet.
- UI controls are shadcn-vue components (`app/components/ui`, add more with `corepack pnpm dlx shadcn-vue@latest add …`): Select for dropdowns, DropdownMenu for actions, Checkbox/Switch, RadioGroup (cards: a Label holding its RadioGroupItem), `Segmented` (ToggleGroup) for pill choices, Tabs, NumberField, Tooltip on icon buttons. No native `<select>` or checkbox (SPEC M2.10). Their state classes (`data-checked:`, `data-active:`, `data-open:`) work through the custom variants in `main.css`; reka-ui sets `data-state`. Class names on reka-based components may not get a parent's scoped styles: pass Tailwind classes. Tests drive a Select by clicking its trigger, then `getByRole('option', …)`.
- Design is an editor since M2.8: a rail of compact rows (drag ⠿, eye), an inspector for the selected item, the phone (`PhoneStage`). New per-slide settings go in the inspector, not the rail. The template is picked in New recap only. Scroll panes get `relative`: without it `sr-only` labels inside them stretch the whole page (`editor.mjs` checks no tab scrolls the page).
- The app UI (sign-in, home, workspace) follows the landing's look since 2026-10-11 (SPEC §6.4): Outfit, the landing's ink/greys/blue tokens in `app/assets/css/main.css`, pill buttons, handwritten notes sparingly, no stickers or illustrations. Recaps keep Geist + Google Sans Code.
- The landing speaks to any business: example business names only appear inside the example phone (the landing e2e checks this).
- The landing scores 100 in every Lighthouse category on mobile and desktop (SPEC M2.11); re-run Lighthouse on a production build after changing it. It is prerendered, and `modules/landing-first-paint` rewrites its HTML at build time (CSS inline, its latin fonts preloaded, the app's script only after the largest paint). So: everything it shows must work from the HTML alone, the headline and lede never fade in from invisible, and nothing in its HTML may depend on the request (absolute URLs come from `siteHref()`/`useCanonical()`; `useRequestURL()` there is the build host).
- Terms and privacy (`/terms`, `/privacy`, SPEC M2.12) describe what the product really does with data. When data handling changes (a new provider, a new field in a payload, a new cookie, retention), update them and `LEGAL_UPDATED` in `app/data/legal.ts` in the same change. Legal name HighReel, contact hello@highreel.app (`app/data/legal.ts`). They're prerendered and rewritten like the landing (`FIRST_PAINT_ROUTES`) and must keep Lighthouse at 100.
- Search (SPEC M2.11): public pages get `useCanonical(path)` and a description; new public pages go into `server/routes/sitemap.xml.ts`; private ones get `X-Robots-Tag: noindex` in `routeRules`. robots.txt must not block `/r` or `/api/r/` (link previews read them; a blocked page can't say noindex). Structured data on the landing says only what the page shows.
- Business-type templates (`shared/templates/starters.ts`) sit on top of the sheet templates; New recap, the Brand panel and the landing's examples all read them. Their copy keys must exist in their sheet template (`tests/starters.test.ts`).
- A page's global styles on `body` hang off its own body class (`recap-page` for `/r`, `example-page`, `unsub-page`): in dev a server render also links the CSS of pages opened earlier, so two pages' global rules on one selector override each other there (this failed `editor.mjs`'s backdrop check, M2.14 P0).
- Light/dark on the public pages (`ThemeToggle`) is the app's own `@nuxtjs/color-mode` setting (`dark` on `<html>`, set before the first paint). Landing and legal colours are variables with a dark set; in scoped styles write `:global(.dark .landing)`, never `:global(.dark) .landing` (Vue drops everything after the `:global()`). Recaps don't follow it.
- The wordmark is `<Wordmark />` (`app/components/Wordmark.vue`, SPEC §6.4). Two logos are drawn there and in `scripts/brand.mjs`, and `LOGO` in `app/data/brand.ts` picks the site's (then `node scripts/icons.mjs` and `node scripts/og-landing.mjs`): **highlighter**, the site's ("highreel" with a marker stroke behind "high", drawn once per visit), and **capital-h**, kept for later ("Highreel" with a blue play as the H's crossbar). `still` for footers. Use it wherever the brand name stands as a logo; don't type "highreel" as a plain-text logo. Images of the logos (icons, `og.png`, `brand/<logo>/`) come from `scripts/brand.mjs`; its shapes must match the component's (`tests/brand.test.ts`), and `tests/e2e/wordmark.mjs` runs the active logo's checks.
- The landing and terms/privacy scroll smoothly (`html:has(.landing, .legal)` in `main.css`); page changes stay instant through `plugins/scroll-instant.client.ts`. A script there that scrolls and shouldn't glide passes `behavior: 'instant'`.
- Phones on the landing use `PhoneFrame` (iPhone frame, recap edge to edge via `--recap-inset-top`).
- Templates are data in `shared/templates/*.ts`. The column contracts there, in SPEC §4 and in `scripts/generate-sample.mjs` must stay in sync (`corepack pnpm test` checks each sample's planted errors).
- A recap can add its own columns and slides on top of its template (`settings.columns`, `settings.slides`, SPEC M2.7). Wherever a campaign or a recap payload is at hand, read its template with `templateFor(template_key, settings)`, not `getTemplate()` (that's the template alone). New scenes join the library in `shared/templates/own.ts` (`SCENES`, `scenesFor` per data kind), `SCENE_TIMING`, `RecapSlide`'s map and Design's `SCENE_ICONS`, and follow the scene rules below; `library.mjs` and the budgets cover each (27 since M2.10).
- Recaps only receive the columns a template's slides read (`toRecapRecipient`); never the id or email.
- Logos are stored as PNG: the link-preview renderer (resvg wasm) can't decode WebP.
- No third-party trackers on recap pages (`/r/*`). Keep `/r` lean: no sign-in code (`useAuth` is plain `$fetch` to `/api/auth/*`; Turnstile's script loads only from `BotCheck`, on `/login` and the demo banner), no toasts/tooltips (they live in `layouts/default.vue`); JS ≤ 150 KB gzipped. Never lazy-import `RecapPlayer` itself (`LazyRecapPlayer`, `import()`): the bundler then puts a helper the player needs into whatever chunk it likes, and `/r` once pulled 21 KB of workspace code for it. The landing lazy-loads `LandingPlayer` instead. Check `/r`'s JS with `tests/e2e/budgets.mjs` after adding shared code or UI libraries.
- Recap scenes: animate only transform and opacity, base style = end state (reduced motion sets `animation: none`), timing from data via CSS variables, randomness seeded. Avoid class names that are Tailwind utilities (`ring`, `outline`, …): Tailwind generates them from the templates.
- "Save image" opens the save picker (SPEC M2.13): `RecapStill` draws any slide at its end state, `RecapSaver` captures ticked ones with modern-screenshot (imported only there; keep it out of `/r`'s first load). Since scenes double as saved images, they must look finished with `is-reduced` and nothing may depend on a clock to show its value. In recap CSS never write a literal `url(` inside a data URI (encode it as `url%28…%29`): the capture reads it as a file to fetch.
- Every business sees only its own data (SPEC M2.14 P1; D1 has no row-level security). Workspace routes call `requireUser(event)` and pass its `db` to the data layer, `server/utils/db.ts`, where all workspace SQL lives: every statement binds `db.businessId` and filters by it (recipients through `campaign_id in (select id from campaigns where business_id = ?)`), on updates and deletes too. Routes never write SQL. Token-addressed routes (`/api/r/*`, unsubscribe) use `tokenDb` in `recap.ts`/`unsubscribe.ts` and look rows up by token only. What RLS's column grants did is "no function for it": nothing writes the counters, rewrites or clears the send log, writes opt-outs (except unsubscribe) or edits bounces. `tests/isolation.test.ts` reads the SQL; run `corepack pnpm check:isolation` after touching the data layer or routes.
- No route holds a whole sheet (a Worker has 128 MB): the grid loads pages of 5,000 rows (`PAGE_ROWS`, `?after=`), sheets upload in parts of 5,000 (`{ part, parts, rows }`, one D1 `batch()` each, `campaigns.import_next` remembers an unfinished one), publish and the column menu check the sheet a page at a time (`server/utils/sheet.ts`), the links file streams. D1 takes at most 100 bound values per statement: many rows go in one JSON parameter (`json_each(?)`, `jsonChunks`).
- Files live in R2 (`MEDIA`), keyed `{business_id}/logo/…` and `{business_id}/{campaign_id}/…` (link previews under `og/`). Browsers only get signed `/media/{key}?exp=&sig=` links (`signMedia`, HMAC from `NUXT_SECRETS_KEY`; 1 h workspace, 24 h recaps); uploads go through `POST /api/media` (type sniffed, ≤ 5 MB), deletes through `DELETE /api/media`.
- Sign-in (SPEC M2.14 P3) is Better Auth inside the Worker, built in `server/utils/auth.ts` (`authFor(event)`), its routes at `/api/auth/*`, its tables in D1 (`migrations/0002_auth.sql`; `tests/auth.test.ts` runs Better Auth's own schema check against the migrations and prints the SQL a plugin or upgrade needs). Pinned at 1.7.7: read its changelog before updating. Who's signed in: `requireUser` / `currentSession` on the server, `/api/session` and `useAuth()` in the browser (no Better Auth client library). Demo and email-link sign-in need a Turnstile token (`BotCheck`; locally Cloudflare's test keys in `.env`). Sign-in links go to `/confirm?token=` (the page signs in from its script, so link scanners can't use the token up) and sign-in emails come from `server/utils/signin.ts` (Email Sending on Cloudflare, Mailpit in dev). After a sign-in, go to `safeNext(next)` only. Keeping a demo moves its business to the account (`keepDemo`, also across devices through `/api/account/keep`); `businesses.owner_id` references the user, so deleting a user deletes the business (its R2 folder needs deleting separately, `removeFolderIn`).
- Server code runs on Cloudflare Workers (`nodejs_compat`, SPEC M2.14 P0), bindings through `bindings(event)` (`DB`, `MEDIA`): no `node:fs`, `os`, `http` or `child_process` at runtime; DNS through `resolve4`/`resolve6`/`resolveMx`, not `lookup` (and Workers answer "no records of this type" with ENOTFOUND); wasm as `?module` imports; SMTP sockets come from `openSocket` in `mail.ts`. The dev server and e2e run on Node and miss Workers-only failures (bundling differs: nodemailer once crashed only there), so after server changes also `corepack pnpm build`, run `wrangler dev` and call the route.
- Recap emails go out through the business's own email account over SMTP (SPEC M2.9), never from an address of Highreel's: no connected account, no email (WhatsApp or the links file instead). Every send goes through `POST /api/campaigns/:id/send` (logged in `email_sends` for the account's daily limit, opt-outs skipped, demo sessions refused). The email is built once in `shared/utils/email.ts` for sending and for Share's preview, with no Recap branding. Saved SMTP passwords are encrypted (`server/utils/secrets.ts`, `NUXT_SECRETS_KEY`) and never returned; the server only connects to SMTP ports and never to private addresses (`smtpTarget`). Locally connect "Local test inbox (Mailpit)" (SMTP 54425, inbox http://127.0.0.1:54424).
- Phone numbers (the `phone` column, WhatsApp) are private like emails: never in a recap payload or on a slide.
- Bounces (SPEC M2.11, `server/utils/bounces.ts`): every send is prechecked (provider typos held, domains without mail bounced) and every failure classified: a bounce goes into `email_bounces` and that business never emails the address again; an answer about the account stops the run with the server's words; a batch with too many bounces pauses. Never send to a bounced or unsubscribed address. `tests/e2e/bounces.mjs` runs its own fake SMTP server.
- Scheduled jobs (SPEC M2.14 P4) keep the privacy policy's deletion promises: demos 30 days after they start, accounts within 30 days of asking, sign-in records when a session ends and rate-limit counts within a day. They're Nitro tasks in `server/tasks/` (no SQL there) calling `server/utils/cleanup.ts`, with bindings from `taskBindings(context)` (no request). `server/schedule.ts` says when; `wrangler.jsonc`'s `triggers.crons` must list the same expressions (`cloudflare.test.ts`), or a job never runs on Cloudflare. Delete a business's R2 folder before its user (cascades take the rows). Logs carry counts, never addresses. Account deletions have no admin route: the owner inserts the address into `account_deletions` (the commands are in `migrations/0003_cleanup.sql`), the one table without a business. Changing a retention promise means changing its job too (and the reverse).
- New tables go in a new `migrations/000N_*.sql` (D1, `corepack pnpm db:migrate`): give them a `business_id` (or reach them through one), put their statements in the data layer with the business filter, and add them to `check:isolation`. Times are ISO text from `toISOString()`, JSON is text with `json_valid`, booleans 0/1.
- Don't put a `font` key back in `components.json`: `shadcn-vue add` would inject a Google Fonts import (a third-party request on recaps).
- No git remote yet; don't push anywhere without asking.
